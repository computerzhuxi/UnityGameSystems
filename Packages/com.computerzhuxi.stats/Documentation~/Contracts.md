# 状态与失败契约

## 状态所有权

业务域通过 `IStatBinding` 持有权威 `Base` 与 `Final`。`StatRegistry` 管理定义、修正和最近一次成功提交的读数；它不会成为另一份业务状态。`GetBase` 每次从绑定读回，`GetFinal` 返回最近一次成功提交的结果。业务域直接修改 Base 后须调用 `Invalidate(id)`；通过 `SetBase` 修改时由 Registry 自动失效。最终值应由 `ApplyFinal` 写入，并能由 `GetFinal` 读回。若业务域在 Registry 外改变 Final，先前已提交读数不会自动更新。

基础值代表永久状态；装备、Buff 等临时影响应使用修正，退出时按精确句柄或 `Source` 清理。`CaptureBaseSnapshot()` 只含基础值，不含修正、最终值或来源；恢复时由业务域重建绑定和临时修正。

## 提交与事件

注册、基础值修改、修正变更和显式失效会触发重算。计算结果先由 `StatDefinition.Constrain` 约束；若结果与上次最终值不同，调用 `ApplyFinal`，再从 `GetFinal` 读回实际值。Base 或读回 Final 任一变化，就发出含前后两组读数的 `Changed`。订阅者收到的事实已提交，可以读取新状态；单纯执行命令而两组读数均未变化时不会发事件。`Changed` 面向观察者；可通过 `IReadOnlyStatRegistry` 限制消费者的写入权限。

`BeginBatch()` 可嵌套。批处理中 `GetBase` 已反映绑定的新值，`GetFinal` 仍是上次已提交值；最外层作用域释放时统一处理失效属性。该机制合并重算，不提供事务回滚。一次提交按 ID 排序处理本轮失效属性；事件回调引发的新失效在下一轮处理。只有 `Changed` 观察者允许同步重新调用同一 Registry；连续超过 64 轮视为回调循环并抛异常。绑定和策略的委托中不能同步调用同一 Registry 的公共 API。

## 非法输入与异常

- 定义 ID、修正类别和来源不能为空或空白；同一 Registry 中重复 ID 被拒绝。上下限必须是有限数，且下限不能大于上限。
- Base、修正值、策略结果、绑定读回的 Final 必须为有限数。默认策略只支持 `Flat` 与 `Multiplier`；不支持的类别在加入或更新时被拒绝。
- `Register` 首次重算失败时撤销该次注册；绑定已发生的外部副作用不保证回滚。`AddModifier` / `UpdateModifier` 在失效提交失败时恢复原修正记录；已发生的绑定副作用仍不保证回滚。
- 一轮中某属性提交失败，不阻止其他失效属性提交；失败属性保留失效状态供后续显式失效重试。观察者异常逐个收集，其他观察者仍会收到已提交变化。错误以 `AggregateException` 汇报。此前成功提交的值与事件不会回滚，因此批处理也不是事务。
- 释放注册会移除其修正，但不会把业务域 Base/Final 重置。无效修正句柄的更新和移除返回 `false`；`RemoveSource` 只按完全相同的来源字符串匹配。

组件初始化先从定义资产创建运行时定义，再为每项 ID 向 `IStatBindingProvider` 请求绑定。资产缺失、空定义、提供者缺失或绑定缺失都会使初始化失败；失败时组件仍未初始化。成功后 `Initialize` 再次调用直接返回，配置变化需要由业务方另行安排新实例。组件 `OnDestroy` 释放注册，不重置绑定中的业务值。
