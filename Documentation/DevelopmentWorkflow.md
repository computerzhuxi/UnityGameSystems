# 可复用系统开发流程

## 修改位置与入口

在 `Packages/<package-id>` 修改唯一正式源码；Lab 通过本地 UPM 路径引用它。通用规则和通用组件进入包，ARPG 的命中、成长、奖励、状态机、UI、存档格式及适配留在 ARPG。改变公共行为前先列出组件式与编程式入口的共同契约、权威状态、生命周期、序列化风险与消费项目调用。

修改后同步包测试、Sample、随包文档及 CHANGELOG。包 README 指向 GettingStarted、API/Contracts；仓库文档只维护开发、验证和发布流程。消费项目主动升级固定标签并验证，不能修改 `Library/PackageCache`。

## 按用途验证

|用途|何时运行|证据|
|---|---|---|
|Contract|修改规则、公共命令或事件时|定向包测试；两种入口共享的行为应有断言。|
|Integration|修改组件、序列化、Sample、Lab 或消费适配时|相关 EditMode/PlayMode、真实场景/Prefab 和业务链。|
|Validation|发布候选、版本引用或高风险迁移时|完整包与 Lab、独立 Sample、构建/冒烟、干净 Git 安装和适用的人工验收。|

这些是选择测试的目的，不要求新增目录。开发中先运行相关测试；候选发布才做完整验证。Editor/Gizmo 修改补人工视觉；纯文档检查链接与渲染；manifest/lock/标签改动做干净导入。消费项目仅通过公共 API、真实组件和业务链验证。

具体测试选择、证据和停止条件见 [测试规范](TestingStandard.md)。

## 工具入口

启动前检查对应 Lab 是否被编辑器占用；存在用户正在使用的实例时协调关闭，不自动结束用户进程。三个入口使用相同参数：`-MirrorOnly` 只读核对 Sample 镜像、不需 Unity；默认提供 `-Platform EditMode|PlayMode -TestFilter '<测试名或筛选表达式>'` 做定向测试；`-Full` 才运行两种模式、构建和 Standalone 冒烟。`-TimeoutSeconds` 与 `-SmokeTimeoutSeconds` 可调节超时。每轮日志、XML 和结果 JSON 放在独立的 `Artifacts/Logs/<System>/<时间-随机码>`；脚本拒绝覆盖已有证据，并要求 XML 中实际有通过的用例。

    ./Tools/ValidateHealth.ps1 -MirrorOnly
    ./Tools/ValidatePerception2D.ps1 -UnityEditor 'D:/Unity/Editor/6000.3.21f1/Editor/Unity.exe' -Platform PlayMode -TestFilter 'PerceptionLifecycleTests'
    ./Tools/ValidateNavigation2D.ps1 -UnityEditor 'D:/Unity/Editor/6000.3.21f1/Editor/Unity.exe' -Full

完整模式仍需人工核对视觉/听觉以及运行后的动态字体、TimeManager、渲染设置、ProjectSettings、meta、GUID 和非目标资产差异。报告区分本轮和历史证据；提交使用显式白名单。Unity 进程不得与已打开的对应 Lab 同时操作同一工程。

## 禁止事项

- 不把凭据写入 Git URL、manifest、脚本或日志；不让公共包引用具体游戏。
- 不在多个项目维护同一运行时实现，不让 Sample/Lab 无保护地复制同一文件。
- 不覆盖已发布标签，不把旧构建或旧测试当成本轮结果。

## 整体重构与任务协作

先核对实际系统库、消费项目和任务工作目录，记录各自 HEAD、工作区修改与当前依赖。整体审计覆盖 Runtime、组件、公开契约、程序集、测试、Samples、Lab、文档和工具；逐层判断是否需要修改，不为统一外观强拆程序集或重写已稳定的实现。

用户要求分任务协作时，先划定每个任务的文件范围、共享文件负责人、依赖和停止点。复杂仓库可先完成一个系统试点，再推广约定。交接包括基线、既有修改、目标与非目标、兼容约束、验证要求、证据路径，以及提交和发布权限。本轮使用 GPT-6-Sol/high；以后按任务复杂度和用户指定选择，不把本轮型号作为架构要求。

执行任务完成后直接通知主任务，不建立定时检查。主任务按完成顺序逐项核对实际差异、测试证据和文档；一个任务必须先完成复核并反馈，再检查后一个。复核期间收到其他完成通知先排队。返修完成后重新复核，执行任务的总结不能替代主任务检查。

## 保持 API 与组件兼容

内部实现可以演进，对外兼容需同时检查三层：

|层面|需要保持的约定|
|---|---|
|代码调用|公开类型、程序集、方法签名和返回值语义。|
|Unity 资产|脚本 GUID、组件身份、序列化字段和持久化事件绑定。|
|运行行为|状态归属、事件顺序、更新时间、启停与销毁责任、非法输入处理。|

内部算法、缓存或分配优化优先保持上述约定，并用公共行为回归验证。修复错误也要检查消费者是否依赖旧行为；签名不变不代表行为兼容。确需改变公共设计时，记录影响，优先提供新入口与过渡适配；不能兼容的变更按发布流程安排版本和迁移。测试通过只证明已覆盖的约定，不代表 API 永久定型。

## 验证证据与异常处理

- 生命周期测试放在能真实触发生命周期的模式中。例如运行时销毁需使用 PlayMode、实际激活对象和逐帧等待；不能用反射直接调用回调来替代真实生命周期。
- 区分编译失败、测试断言失败、未进入测试的环境失败。许可证、UPM 或工程占用导致启动失败时，保留日志并记为阻塞，不能算测试失败或通过；环境没有变化时避免重复启动。
- 以本轮输出中的实际路径读取 XML，核对筛选到的具体用例、数量及结果；日志可能位于 Lab 等子目录，不猜测路径，不凭进程退出或旧结果宣布通过。
- GUI 验收交给用户时，列出工程路径、场景或资源文件、操作顺序及具体预期现象；用户反馈后再记录通过，并注明结果来源。自动测试不能代替这项反馈。
- Unity 运行前后比较工作区。只清理能确认由本轮运行产生的非目标变化；原有修改和来源不明的文件保留。Windows 脚本按支持的 PowerShell 版本检查编码，避免只在 PowerShell 7 正常。

## 收尾与授权边界

分别报告实现、复核、针对性自动验证、人工验收、提交、推送、版本发布和消费项目升级的状态。开发阶段可以在计划内验收完成后收尾，并明确未执行的 Standalone、干净安装等发布检查；不能因此宣称版本已发布或消费项目已升级。

提交前核对最终差异并显式选择目标文件；提交信息使用英文类型和中文描述，例如 `refactor: 完善系统双入口`。保留已有无关修改，不以整个工作区绝对干净作为完成条件。提交、推送、打标签发布和消费项目升级分别按已有授权执行；未授权的后续阶段不自动开展，已授权的步骤不重复询问。提交后记录 SHA，推送后核对目标分支。

长期流程记录可复用规则；具体用例、失败日志、人工反馈、提交与发布状态放在本轮验收记录。每次状态变化及时更新记录，避免完成后仍写着“许可证阻塞”“尚未测试”或“尚未提交”。
