# UnityGameSystems 测试规范

## 任务下发与验收

主任务下发前明确可观察的验收行为、变更风险和影响范围，并写出必须新增或运行的测试、扩大验证的触发条件及停止条件。执行任务实施验证并提交证据；主任务核对实际代码、差异和结果。测试规模由风险决定，不以代码行数或测试数量判断是否过度，也不设固定用例上限。

单任务优先运行定向测试。多个任务整合时，根据公共契约、共享文件、依赖和消费者的交叉影响补测；冲突解决或依赖变化使既有证据失效时，重验受影响范围。已通过且相关代码、资源和依赖未变的验证无需重复。发布候选按发布流程扩大验证。

## 选择测试方式

规则与计算优先使用快速 EditMode 测试；依赖 Unity 生命周期、物理或跨帧行为时使用 PlayMode，并真实触发对应行为。EditMode 和 PlayMode 是运行环境，不分别等同于单元测试和集成测试。选择测试时同时考虑行为层级：纯规则、公共 API、组件与资源、真实入口和消费者业务链。改变入口接线或公共行为时验证实际入口；已有自动集成测试能覆盖同一风险时直接复用，不在各层重复证明同一规则。

GUI 验收交给用户。执行任务提供工程路径、场景或文件、操作步骤和具体预期现象；收到用户反馈后才记录人工结果，并注明来源。自动测试不能替代需要视觉或交互判断的验收。

普通功能改动进行编译自查、定向自动测试、必要的接入验证和适用的人工验收。默认不运行全量测试、构建、清理 Library 或干净安装；仅在影响范围、发布要求或明确风险需要时扩大。若零分配或性能指标是明确的公共承诺，改动相关路径时按风险运行相应验证，不推迟到发布。修改算法且既有结果预期（oracle）可能受影响时，使用独立预期或可信对照核查结果，避免新实现与新测试共享同一错误假设。

## 编写测试

明确规则和可复现缺陷优先采用 TDD：先让测试因预期原因失败，再实现修复、确认通过，最后重构。探索性原型可先验证设计，行为稳定后补覆盖公共行为的测试；不机械强制每一步都先写测试。

新增测试须说明它证明的具体风险与可观察行为。避免锁定内部实现、为测试扩大公共 API 或搭建无必要的框架。测试数量由行为和风险决定。相关测试在同一工程内集中运行；不并发启动争用同一工程的 Unity 进程，也不自动结束用户正在使用的编辑器。

## 证据、阻塞与停止

以本轮实际输出路径读取测试 XML，核对筛选到的具体用例、数量和结果；进程退出码、旧日志或空结果均不能单独证明通过。区分编译错误、测试断言失败和启动前环境阻塞。许可证、UPM、工程占用等环境问题保留日志；条件未改变时不重复尝试。可记录启动、导入及测试耗时，用于改善后续验证效率。

当验收行为有证据、必须运行的测试通过、相关错误已解释，且后续修改没有使证据失效时停止本轮验证。报告列出验证内容与命令、对应代码状态、具体结果和证据路径、未执行项及人工验收状态。发布检查与开发阶段验证分别报告。
