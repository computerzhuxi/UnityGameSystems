# Unity 可复用系统提取手册

这份手册沉淀自 Health 与 Perception 2D 从 ARPG 内部模块变成独立 UPM 包的完整过程。Health 代表可拆分纯 Core 的数据系统，Perception 2D 代表依赖 Unity 物理、需要 Gizmo 和人工视觉验收的引擎型系统。它用于指导以后提取其他系统，而不是要求所有系统照搬某个现有包的代码结构。

## 最终目标

完成后的系统应满足：

1. 正式源码只有一个归属位置。
2. 不引用任何具体游戏项目。
3. 可以在独立 Unity 工程中开发、测试和构建。
4. 消费项目无需修改包源码，只通过公共 API 或项目适配层接入。
5. 状态只有一个权威拥有者。
6. 发布版本由不可变 Git 标签锁定。
7. 旧项目可以不升级，新项目可以稳定复用。

完整流程：

    调研与候选评估
       ↓
    现状基线与行为矩阵
       ↓
    逻辑边界
       ↓
    独立包与 Lab
       ↓
    原项目适配迁移
       ↓
    独立验证与发布
       ↓
    Git 版本回接
       ↓
    独立复核与文档收口

## 零、先调研再立项

提取不是把现有目录直接变成包。开始实现前应先完成：

1. 调研官方文档、成熟引擎或可信开源实现，记录可借鉴的职责划分。
2. 检查参考实现的许可证；参考设计思想与复制代码必须明确区分。
3. 写出通用语义、当前项目语义、明确不包含的能力和未来可能扩展。
4. 判断现有模块是应整体提取、拆出较小核心，还是继续留在项目内。
5. 形成简短提案，经确认后才进入实现。

调研结果不是功能清单。只实现当前已证明稳定、能被多个项目共享的最小契约，不因参考系统功能丰富就一次性复制全部能力。

## 一、判断是否值得提取

|判断项|适合提取|暂不适合提取|
|---|---|---|
|业务语义|多个游戏基本一致|只服务当前玩法|
|依赖|少而稳定|依赖大量项目类型|
|数据归属|拥有明确状态|只是跨模块编排|
|公共接口|能够描述稳定契约|接口仍频繁试验|
|验证|可以脱离原项目测试|必须加载整个游戏才能运行|

Health 值得提取，因为当前生命、生命上限、伤害、治疗、死亡和复活具有稳定通用语义。命中、护甲、无敌、奖励、UI 和动画没有一起提取，因为它们属于具体游戏业务。

遇到以下情况应暂缓：

- 为了独立必须把半个项目一起搬走；
- 公共 API 中出现 Player、Enemy、Quest 等项目概念；
- 每个项目都需要修改包内部代码；
- 系统没有自己的状态或规则，只是调用多个模块；
- 还无法说清楚它负责什么、不负责什么。

## 二、建立重构前基线

提取前先证明项目当前能正常工作，否则提取后无法区分旧缺陷与新回归。

至少记录：

- Git 基线提交和工作区状态；
- Unity 与依赖版本；
- EditMode、PlayMode 和构建结果；
- Scene、Prefab、ScriptableObject 数量；
- Missing Script、meta 缺失、孤立和重复 GUID；
- 关键配置、序列化字段和 UnityEvent；
- 目标模块的上游消费者与下游依赖；
- 用户已有且不能覆盖的工作区修改。

机器可读结果和日志放在被 Git 忽略的 Artifacts，不混入正式源码提交。

## 三、先做逻辑边界，再移动文件

不要一开始就创建 asmdef 或复制代码。先在原项目中回答：

1. 系统唯一拥有的数据是什么？
2. 谁可以提交修改命令？
3. 谁只能读取或监听？
4. 哪些规则是通用规则？
5. 哪些规则属于当前游戏？
6. 系统允许依赖哪些基础能力？
7. 哪些项目类型必须从系统中移除？

推荐方向：

    游戏上层模块 ──▶ 系统公共契约 ──▶ 更底层基础模块

不允许系统反向依赖当前游戏的 Player、Enemy 或 UI。

Health 提取前先让生命成为唯一数据拥有者，并从属性系统移除重复的当前生命和生命上限。这个顺序比移动文件更重要。

边界文档至少应记录职责、非职责、真实依赖、数据所有权、公共 API、内部 API、序列化风险和未来程序集依赖。

迁移前还必须建立行为兼容矩阵：

|现有行为或配置|处理方式|验证方式|
|---|---|---|
|必须兼容|原样保留|回归测试与真实资产加载|
|有意改变|写明原因和新语义|用户确认后测试新行为|
|删除|证明没有消费者或明确接受影响|源码、资产和调用方审计|
|项目特有|留在适配层|消费项目集成测试|

不能等测试失败后才决定某个旧行为是否应该保留。序列化配置还要标明它是“仅初始化读取”“运行时实时生效”还是“必须通过公共命令修改”，避免 Inspector 看似可编辑却不会影响运行中状态。

## 四、设计包的层次

规则能脱离 Unity 时，优先采用：

    通用 Unity Component ──▶ Core ──▶ .NET 标准库
    具体游戏适配层 ─────────▶ Core

- Core 保存规则和唯一权威状态，不依赖 Unity。
- Unity 层负责 MonoBehaviour、Inspector、UnityEvent 和序列化接入。
- 游戏差异留在消费项目适配层。

不是所有系统都必须强制拆两层。如果系统天然依赖 Unity 物理、动画或资源生命周期，而且纯逻辑层没有独立价值，可以保留一个清晰的 Unity 包。

系统应说明两个接入入口：组件式入口由 MonoBehaviour、Inspector 与序列化装配；编程式入口让调用者通过公开类/接口自行组合和驱动。编程式入口可以使用 Unity 类型，不强制成为纯 C# 程序集。两者共享规则、事件顺序与唯一权威状态；不为形式统一拆程序集，也不把所有内部实现公开。分别记录创建、绑定、启停、销毁或释放时的生命周期责任。

公共 API 应遵循：

- 命令和查询分离；
- 观察者优先获得只读接口；
- 对适合同步返回变化结果的命令，可通过返回值说明是否变化及前后状态；其他命令可通过查询或事件提供这些事实，不强制每个命令都返回结果；
- 非法输入、无变化、事件顺序和异常具有明确契约；
- 不为了测试方便公开内部实现；
- 不提前加入尚未出现的扩展点。

## 五、建立正式包与开发 Lab

推荐结构：

    UnityGameSystems
    ├─ Packages/com.example.system
    │  ├─ Runtime
    │  ├─ Tests
    │  ├─ Samples~
    │  ├─ Documentation~
    │  ├─ README.md
    │  ├─ CHANGELOG.md
    │  └─ package.json
    └─ Projects/SystemLab

包目录是唯一正式源码。Lab 通过本地 UPM 路径引用包，用于开发期间即时验证。

Sample 与 Lab 承担不同职责：Sample 教使用者如何接入，Lab 负责开发、测试和构建。两者不应无约束地复制同一份源码；若确实需要镜像，必须指定唯一权威来源，并提供生成或哈希一致性检查。

Lab 必须证明：

- 包不依赖原游戏；
- 从空 Library 可以导入；
- 测试、Scene、Prefab 和 Sample 可以独立运行；
- 可以完成目标平台构建；
- 新电脑只需克隆仓库，不需要重新创建 Unity 工程。

## 六、迁移原项目

中型项目通过适配层接入：

    Combat / Progression / UI
                │
                ▼
          项目适配层
                │
                ▼
           可复用 Core

适配层负责转换项目配置、保留旧方法和事件、转换业务命令、保护序列化身份并隔离包版本变化。

适配层不得保存第二份权威状态。Health 在 ARPG 中由 CharacterHealth 保留旧接口，但 Current 和 Maximum 只存储在 Health Core。

涉及 MonoBehaviour、ScriptableObject、SerializeReference 或程序集变化时，必须检查：

- 原 meta GUID；
- 类名、命名空间和程序集；
- MovedFrom；
- 序列化字段名；
- Scene、Prefab、配置和 UnityEvent 的真实加载；
- Missing Script 和缺失托管类型。

不要用手工批量修改 YAML 代替 Unity 真实加载验证。

## 七、测试分层

### Core

覆盖正常命令、边界值、溢出、死亡与复活、无变化命令、事件顺序、回调重入、订阅者异常和状态恢复。

这些属于 Contract 验证：针对实际公共行为选取用例。若系统没有独立纯 Core，则在包测试中验证同样的规则，不为了测试目录形式拆程序集。

### Unity 层

覆盖 Inspector 初值、Awake、重复初始化、禁用重启、UnityEvent、Prefab、Scene、非法配置失败后的状态和 Sample 导入。

组件与程序式入口需验证共同语义和各自的生命周期；Lab 场景、Prefab 及消费项目真实接入属于 Integration 验证。

### 消费项目

覆盖真实玩法链，而不只测试适配层单个方法：

    命中 → 最终伤害 → 生命变化 → 死亡 → 奖励 → UI 和状态机

测试可见性必须遵守生产边界：

- 包内部实现只由包自己的测试程序集验证；
- 消费项目只通过包的公共 API 和真实 Unity 组件验证；
- 禁止为了消费项目测试向其开放包内部 API；
- 不为了方便断言而扩大公共 API。

### 测试资源安全

测试不得写入固定 Assets 路径后无条件删除。创建 Unity 资源时：

1. 创建独占测试目录；
2. 使用 GenerateUniqueAssetPath；
3. 保存创建资源的 GUID；
4. 只在路径仍对应该 GUID 时清理；
5. 回归验证已有同名资源不会被覆盖或删除。

这是 Health 1.0.0 复核中发现的重要教训。

## 八、发布候选验证

|环境|目的|
|---|---|
|Lab 本地包|验证开发源码|
|消费项目本地候选包|验证尚未发布的迁移|
|发布前全新 Sample 候选源码导入|证明不依赖原项目；可用本地包，不假定发布提交或远端标签已存在|
|发布后全新 Sample 固定标签导入|验证远端标签及最终安装方式|
|发布后消费项目固定 Git 包|验证适用的最终安装与业务链|
|消费项目隔离副本|排除原 Library 和缓存掩盖的问题|

同时审计实际 DLL 引用、程序集环、反向项目依赖、内容资产差异、meta、GUID，以及测试产生的字体、设置和缓存。

失败结果应保留并解释，不能删除失败证据后只展示最后一次通过。

### 按变更风险选择复测范围

|变更类型|最低复测要求|
|---|---|
|Runtime、公共 API、序列化或行为|开发阶段运行受影响的包与 Lab 测试；发布或迁移阶段补消费项目、资产恢复与干净导入|
|Editor、Gizmo、Inspector 辅助|相关 EditMode 测试与人工视觉检查|
|Sample 或 Lab 交互|独立导入、运行检查与对应人工验收|
|manifest、lock 或标签|按实际固定提交或已发布标签干净导入并运行消费项目测试；新标签推送后另从该标签复验|
|纯文档或图数据|链接、生成器、渲染、幂等和 diff 检查|

高风险变更可以扩大验证范围；低风险变更无需为了形式重复运行无关的 Unity 全套测试。报告必须准确说明哪些证据来自本轮，不能把旧构建冒充本轮结果。

开发中使用 `Tools/Validate<System>.ps1 -TestFilter` 定向运行相关 Contract 或 Integration 测试，Sample 镜像可用 `-MirrorOnly` 独立核对；发布候选显式使用 `-Full` 完成 Lab 的两种测试、构建与 Standalone 冒烟。固定标签安装、适用的消费项目复验及人工视觉/听觉验收另行完成，`-Full` 不代表全部发布验收通过。三者是验证用途，不要求新建目录或测试框架。脚本每轮保留独立日志、有效 XML 与超时结果。

需要视觉判断的系统必须在立项时建立人工验收清单，记录操作、预期现象、观察者和结果。Gizmo、动画、UI、音频与 VFX 不能仅凭自动化测试宣布完成；不涉及视觉或听觉时明确标记“不适用”。

## 九、版本与发布

新包的公共契约仍在探索时从 `0.1.0` 开始；只有准备承诺稳定兼容边界时才发布 `1.0.0`。`0.x` 同样必须使用不可变标签和 CHANGELOG，不能把“实验版本”理解为可以覆盖历史。

|改动|版本|
|---|---|
|兼容错误修复|补丁版本，例如 1.0.1 → 1.0.2|
|兼容新增能力|次版本，例如 1.0.1 → 1.1.0|
|破坏 API、行为或序列化|主版本，例如 1.x → 2.0.0|

发布顺序；具体门禁见 [发布流程](ReleaseWorkflow.md)：

1. 更新 package.json、CHANGELOG 和文档；
2. 完成候选源码验证及发布前独立复核，修正阻断项后重验受影响范围；
3. 按已有授权提交并推送发布提交；
4. 创建并推送带注释版本标签，只读核对远端标签与提交；
5. 从远端固定标签重新安装验证；
6. 适用时由消费项目更新 manifest 和 lock，运行集成测试并按授权提交升级；
7. 独立复核发布后安装、消费项目结果与历史记录。复验失败应记录阻塞，不宣称发布验收通过；已推送标签不移动，修复使用新版本。

标签统一使用 `<system>-v<semver>`，例如 `perception2d-v0.1.0`、`health-v1.0.1`。

标签一旦发布就不能移动。旧版本出现问题时发布新版本，不能覆盖旧标签。

## 十、独立复核

实现报告不是最终结论。复核者应从真实仓库重新检查：

- 两个仓库的 HEAD、工作区和提交范围；
- 远端分支与标签；
- 包源码、发布标签和 PackageCache；
- 关键实现，而不只阅读总结；
- 测试 XML 的真实结果；
- DLL 实际引用；
- 内容资产、meta 和 GUID；
- 失败日志是否如实记录；
- 是否存在超范围修改。

发布前独立复核候选代码、差异与验证证据；通过后按已有授权提交、推送和创建标签。发布后再独立核对远端标签、固定标签安装、适用的消费项目复验及记录，全部通过后才能宣布发布验收完成。复验失败应保留证据并记录阻塞；已发布标签不移动，修复使用新版本。

推荐把实现与复核放在不同任务中：执行任务负责实现、候选验证和报告；复核任务只读检查真实仓库并列出阻断项。修复后再次复核；提交、推送、标签和消费项目升级分别按已有授权执行。

任务交接至少包含：基线提交、已有工作区修改、目标与非目标、行为矩阵、允许依赖、序列化风险、人工验收清单、提交权限、停止点和证据路径。

## 十一、文档收口

|类型|回答的问题|
|---|---|
|包 README 和 GettingStarted|从哪里开始，以及组件式和编程式如何最小接入？|
|包 API/Contracts|公开行为、事件、生命周期与状态所有权是什么？|
|架构与集成文档|为什么这样设计，项目如何接入？|
|开发与发布流程|以后怎么修改和发布？|
|历史验收记录|这个版本当时如何证明通过？|

`package.json` 记录当前源码版本，版本变化写入 CHANGELOG；不可变标签与发布历史证明已发布版本，消费项目实际安装由 manifest 和 packages-lock.json 证明。不要把源码版本自动写成已发布版本，也不要在多份架构文档重复维护“最新版本”。

长期文档与历史证据必须分开：当前用法、契约和流程持续维护；某次 Implementation、Validation、Review、Release 记录统一归档到 `Documentation/History/<System>/<Version>/`。历史报告可以保留当时的失败与候选状态，但应明确它们不是当前安装说明。

仓库首页登记所有系统并链接各包入口；发布事实统一从标签与历史记录核对。提取手册、README 或其他既有修改不能因“保护用户改动”而永久停留在未提交状态，应在发布后作为独立文档变更复核并提交。

### 提交边界与自动生成资产

发布和消费项目提交都使用显式白名单。每次 Unity 运行后固定检查动态字体、`TimeManager.asset`、渲染管线设置、ProjectSettings、测试结果与临时资源。确认由本轮运行产生的非目标自动改写在提交前恢复；不得覆盖基线已有或来源不明的修改。

完成状态不是机械要求所有仓库绝对干净，而是：没有意外修改；开始前已有的用户修改仍被保留，或经确认后作为独立提交处理。

验证入口共享必要的日志、超时、XML 和镜像核对能力，各系统保留自身场景与边界门禁；不要为了通用化构建发布平台。一次性 staging 脚本只能作为本轮证据，不能成为下个系统依赖的隐形流程。

## 十二、完成标准

以下清单针对完整的提取、发布和消费迁移。仅进行现有系统重构时，先明确本轮阶段；未开展的发布或迁移项保留为未执行，不作为开发已完成的证据。日常整体重构、任务协作、兼容维护和环境阻塞处理遵循 [开发流程](DevelopmentWorkflow.md)。
