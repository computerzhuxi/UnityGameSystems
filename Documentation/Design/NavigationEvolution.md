# Navigation 下一版设计提案：优先完善 2D

追加决定（2026-09-17）：用户已批准可选局部避让，详见 [避让设计](NavigationAvoidance2D.md)。本条优先于旧“暂不做群体避让”；3D、战斗站位与自主楼梯仍不做。

日期：2026-09-16。状态：2D 方案已批准并进入 0.2.0 候选实施，尚未发布。用户最新决定：本轮先做好 2D，3D 仅作为未来方向。以下“当前执行范围”优先于后文早期通用化与 3D 草案；后者保留设计参考，不构成本轮待实现事项。

## 当前执行范围（用户最新调整）

### 本轮目标

继续以 com.computerzhuxi.navigation2d 为正式包，保持二维使用方式清晰。下一候选预计为 0.2.0，最终按实际 API 兼容情况确定；不移动已发布 navigation2d-v0.1.0 标签，不自动提交或发布。

1. **两种使用方式**：保留 FindPath 直接查询；新增可选 NavigationAgent2D 纯逻辑封装，负责唯一一份路径、索引、到达和重算状态。Unity 组件只是便利入口，不强制使用。
2. **使用体验**：提供有中文职责注释的最小示例与清晰配置说明，让使用者知道如何提供障碍源、提交目标和消费移动建议。Sample 分别演示直接查询和 Agent；不能依赖 ARPG。
3. **跟随可靠性**：明确 SetDestination/UpdateDestination/Stop/Tick 的语义，覆盖移动目标、必要转角、同格终点、动态封路、失败重试、暂停、重新启用及障碍域改变。安全跳点继续验证整段净空，不再引入追击抖动。
4. **性能证据**：先按查询、跟随和多角色请求统计展开数、障碍调用数、分配及耗时，再针对可测瓶颈优化。优先评估单次查询内重复检查；若缓存，必须绑定半径/网格/障碍域并限定失效时机，不默认建立跨请求缓存。
5. **ARPG 接入**：AI 决策、速度倍率、World 层级规则及实际移动留在项目。采用 Agent 时从 EnemyNavigation 移出路径/索引/时钟，禁止双份权威状态；保留真实生产控制器测试。

### 暂不做

- 3D 代码、地面图、NavMesh 后端、3D Lab 和 3D 依赖。
- 为了未来用途重命名包、强制二维接口使用 Vector3、先建立多包依赖体系。
- 未经实际收益验证的泛型 Core 大改；现有 2D 查询与跟随的内部边界先理清，有明确独立价值再拆。
- 自主上下楼、跨层规划、群体避让、大世界分区或分帧调度。发现真实需求时另行立项，不纳入本轮默认完成标准。

### 当前执行顺序

1. 核对发布后基线、2D API 与性能基准，确定旧行为兼容矩阵。
2. 在独立 Lab 完成纯逻辑 Agent2D、可选组件及两条使用路线的 Sample。
3. 验证到达/重算/失败/失效/安全跟随，按数据选择必要的局部性能优化。
4. 通过公开 API 迁移 ARPG，保持 World/Movement 边界与序列化身份。
5. 完成包、Lab、Sample、ARPG 全量测试/构建、资产审计与人工观察，停在未提交、未打标签、未推送状态，等待独立复核。

后文第 3–6 节涉及新通用包、泛型 Core 与 3D 的内容，以及第 8–9 节中的 3D 实验，均为未来参考；当前执行以本节为准。2D Agent 的状态与错误语义、唯一数据归属、旧行为回归仍可沿用。

## 2. 分层与唯一状态归属

|层|职责|不负责|
|---|---|---|
|Navigation.Core|泛型图 A*、搜索预算、工作区与搜索结果|物理、世界坐标、地面、角色状态|
|空间查询适配|端点解析、节点与边、路径生成、通行验证、域版本|决定追谁、伤害、动画|
|NavigationAgent 纯逻辑|目的地、唯一一份路径与索引、失效、到达、重算|写 Transform/Rigidbody/CharacterController、决定空间层级|
|Unity 可选组件|Inspector 配置、生命周期、只读调试；组合纯逻辑 Agent|另一份路径状态、第二套搜索算法|
|ARPG 适配|AI 决策、速度倍率、World 障碍域、CharacterMovement2D 命令|复制包内部路径与重算时钟|

依赖方向为项目/Unity 适配 → 通用契约与 Core。2D 和 3D 适配彼此无依赖。组件可分别叫 Agent2D/Agent3D，但共享纯逻辑实现；不为统一名称强迫二维用户转换 Vector3。

## 3. 未来参考：通用包与兼容策略

拟新增 com.computerzhuxi.navigation（探索期 0.1.0），提供无 Unity 的 Core、2D 适配和纯逻辑 Agent 的独立程序集。先用真实依赖验证程序集隔离，而不是把所有内容放在一个 Runtime asmdef。

旧 com.computerzhuxi.navigation2d@0.1.0 继续可安装，不重命名已发布包或移动标签。ARPG 先保持旧版本，等新包的兼容矩阵与 Agent 通过后在候选分支主动迁移。新旧版本可共存用于比较，但同一角色只启用一个导航状态拥有者。若提供旧 API 外观，应在新版本中转发共享实现，不复制算法；多包依赖必须验证固定 Git 标签解析，不能假设 UPM 自动寻找同仓库兄弟包。

版本号与最终包拆分在技术验证后定案；此处不宣称已经发布新版本。

## 4. 未来参考：泛型 Core API 与算法契约

以下为概念签名，不是现有可调用 API：

    INavigationGraph<TNode>
        GetEdges(node, reusableBuffer)
        EstimateRemainingCost(node, goal)
    NavigationEdge<TNode> = destination + cost
    AStarSearch<TNode>.FindPath(graph, start, goal, options, output)

- 节点必须有稳定的相等性与哈希；允许显式 EqualityComparer。
- 边代价有限、非负，启发值有限、非负；非法图数据与源异常有明确错误/异常语义。
- 采用 double 代价并检测累加溢出；原 2D 10/14 值可精确保留。
- 支持已关闭节点在发现更低代价时重新打开；最优性要求启发函数可采纳且终点启发为零，不承诺任意用户启发都最优。h=0 可作为对照，无需另写一份 Dijkstra 实现。
- 稳定邻居顺序与 F/H/发现序号 tie-break；相同图与比较器下确定性。
- 单次查询图必须稳定；禁止实例重入与并发共享工作区。失败清空路径，不返回伪完整结果。
- 最大展开次数（重开后再次展开同样计数）、最大边检查次数与工作区上限分开约束；单个第三方回调本身耗时无法由这些计数限制。
- Core 不公开 Physics2D 特有失败。端点落地、身体净空等由空间层细分结果，不能把 StartBlocked 等全部压成 InvalidInput。
- 用独立最短路基准验证带权/有向/零代价边、重开节点、不可达、起终点相同、预算和异常恢复；用对照数据测量泛型抽象开销与预热分配。

## 5. 空间与 Agent API 草案

    INavigationQuery<TPosition>.FindPath(request, output)
    INavigationTraversal<TPosition>
        DomainRevision
        CanTraverse(currentPosition, nextPosition)
        HasArrived(currentPosition, destination, tolerance)
    NavigationAgent<TPosition>
        SetDestination(destination)
        Tick(currentPosition, deltaTime)
        Stop()
        RequestRepath()
        HasPath / NextWaypoint / State / LastResult / PathRevision

实际坐标由适配器定义：2D 使用 Vector2，地面适配使用含表面身份的地面位置/Vector3 请求。Agent 不能自己用通用欧氏距离判断桥上下已经到达；到达与目标偏移策略由空间适配提供。

Agent 状态首版为 Idle、Following、Arrived、Failed；同步查询没有真正 Pending，不添加一直为 false 的 IsPathPending。未来分帧查询应通过独立请求句柄扩展，不提前伪装异步。

- SetDestination 首次建立意图；重复相同目标不清空进度、不立即重算。Update/Tick 分离，时间由调用方输入，暂停不消耗计时。
- 目标偏移超过阈值后请求重算，最低重算间隔可配置；域失效与当前段受阻立即停止旧移动建议，是否立即重算明确区分预算策略。
- 重算失败不继续沿旧目的地路径；失败重试按间隔进行。状态变化与结果只读可查询，首版不引入复杂同步事件重入模型。
- 路径点跳过必须验证完整新连线；保留现有“不能切掉必要拐点”与“重算不回头对齐起点格中心”的回归。
- Agent 是路径唯一拥有者；直接低层调用时则由调用方拥有输出，两条使用方式互斥组合到具体角色。
- 导出只读路径视图的有效期写明，不把内部可变 List 暴露给消费者。配置使用初始化快照，运行期修改必须走显式 Reconfigure 并使路径失效。

## 6. 未来参考：3D 地面范围与后端选择门槛

首版地面模型：固定世界 +Y 为上，站立胶囊体，无飞行、跳跃、攀爬、蹲伏、移动平台和任意重力。起终点必须解析到明确可站立表面。配置含半径、总高度、最大坡度、上台阶高度、下台阶高度、端点投影距离及接触容差，非法配置拒绝而非静默修正。

地面与障碍可以来自同一几何体：不能简单把整个地面 Layer 从净空查询排除，否则地面网格的竖直侧壁可能失去阻挡。端点重叠检查与扫掠分开做，脚底接触容差必须有测试。

|方案|价值|风险与本提案决定|
|---|---|---|
|Unity NavMesh 地面查询后端|已有坡度、角色尺寸、台阶与连接建图能力|建议作为首个 3D 技术验证基准及优先候选；需要显式 AgentType/区域/表面域绑定及动态变化处理|
|自有分层地面图 + Core A*|可复用自有搜索工作区、计数预算及图数据|需要自行证明地面覆盖、台阶通行与桥上下拓扑；先做小型原型，不直接承诺成为首版正式后端|
|普通 XZ 二维格 + 向下首个命中|实现简单|拒绝作为通用方案：同列多表面会丢失桥下/桥上身份|
|三维体素自由移动|适合体积空间|不属于本次地面角色需求|

两种候选都必须在同一 Lab 场景测量。Unity NavMesh 后端调用自身路径查询，不会经过自有泛型 A*；共享的是请求/结果/Agent 契约，不能声称整套系统只有一种搜索实现。若要求所有 3D 也经过自有 Core，需要采用自有地面图并接受其额外开发与验收成本。

Native 查询的节点展开数量通常无法通过公共查询接口获取，不能返回伪造预算指标；后端能力应明确声明 SupportedLimits。首版同步 NavMesh 查询不能承诺严格毫秒截止或沿用 Core 节点预算。不支持的限制应明确拒绝或要求调用方选择该后端支持的策略。

### 地面安全约束

1. 端点使用小范围显式投影，禁止靠大范围“最近点”悄悄选到楼上。需要调用方的表面/域约束与可达性检查；NavMesh 的 AgentType/AreaMask 本身不等于任意地图实例隔离。
2. 自有地面图节点至少携带稳定表面身份与采样位置；不能仅以 XZ 或高度四舍五入作为身份。图重建递增版本，旧句柄和路径失效。
3. 相邻端点都可站立不代表边可走。坡道需要连续地面支持；台阶需要验证抬升、水平前进、落地过程和最终净空。未经验证不能把连接简化成两端直线。
4. 单根向下射线和离散点采样无法对任意窄裂缝提供绝对连续保证。若自有原型依赖采样，必须定义支持的最小几何尺度、采样间距与保守失败条件；不能把未采到的空洞视为证明安全。
5. 桥上桥下可以共存但必须通过真实坡道/楼梯拓扑相连。邻近高度或 CapsuleCast 无碰撞不构成连接证据。
6. 动态障碍出现时先阻止使用受阻段，再请求重算；障碍几何、导航建图版本与物理同步各自有明确时间点，不承诺“Collider 改了 NavMesh 立刻更新”。
7. 本阶段不实现特殊通行链接。普通可行走台阶/坡道与游戏楼梯状态编排分离，不能把 ARPG SpatialLevelTransition 搬入通用包。

|现有行为|下一版要求|

## 8. Lab 与量化验收

建立 NavigationLab，保留 2D 对照区、3D 地面区及纯图测试；正式代码只在包中。Sample 分别展示直接查询、Agent 组合两条使用路径，角色运动器只是 Sample/Lab 的示例。

3D 场景与断言：

- 平地/绕墙：完整路径、身体不穿墙、目标移动重算稳定。
- 坡度阈值内/外：按配置可走/拒绝，边界容差固定。
- 上/下台阶阈值内/外：分别验证；低顶台阶不能仅因高度合格就放行。
- 断崖、窄裂缝、没有地面：拒绝未支持的跨越，不能悬空连接。
- 低顶与窄门：不同身高/半径得到相应结果。
- 桥面/桥下相同 XZ：不错误吸附、不直接跨层、不以水平距离宣告到达；有坡道时可真实连通。
- 动态门关闭/开启：停止旧段、失败/重算/恢复路径均明确。
- 不可达、端点非法、投影歧义、图版本过期、预算耗尽：结果可区分；不得把部分路径标为完整成功。
- 多个导航域及物理场景：无跨域泄漏，特别验证 NavMesh 场景装载行为，不能假设它与 PhysicsScene 一一对应。

性能测试分开测 Core、2D 物理、3D 后端与 Agent，记录固定随机种子、节点/边次数、物理调用数、预热分配、p50/p95/max 和总帧成本。对照已发布 0.1.0；不预先宣称性能提升，不以增加算法选项代替测量。

验收包括独立空 Library 导入、Edit/PlayMode、Sample 独立导入、Standalone 和运行、实际 DLL 无 Unity Core 引用/无 ARPG 反向依赖、资产/GUID/序列化与固定 Git 标签消费。坡道、台阶、低顶、桥上下及 ARPG 追击必须人工观察。

## 9. 历史草案：包含 3D 的执行顺序（本轮不执行）

1. 冻结兼容矩阵和基准场景；记录两仓库基线及用户资产修改。
2. 纯 Core 原型与二维适配对照；通过独立最短路基准和旧行为测试后才替换候选实现。
3. Agent 纯逻辑及组件薄壳；在独立 Lab 验证唯一状态归属、到达、失效、重算和停止。
4. 在同一 3D Lab 对比 NavMesh 与自有分层地面图原型，记录安全边界、预算可控性、代价与依赖，作出后端 ADR。若自有方案不能证明断崖/多表面正确性，不强行产品化。
5. 选定地面后端、固化包拆分/API，再迁移 ARPG 2D 适配并执行全量回归。
6. 独立复核与人工验收后另行授权发布；本提案不继承上一轮 0.1.0 的发布授权。

## 10. 一手资料与解释边界

核对日期 2026-09-16；引擎文档为 Unity 6000.3，AI Navigation 参考 2.0 文档，实际依赖精确版本在技术验证时由 Unity 6000.3.21f1 解析并锁定。只参考官方职责与接口，不复制实现代码；若采用 AI Navigation，其许可证与包依赖需在落地阶段检查安装包 LICENSE 后记录。

- [Physics.CapsuleCast](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/Physics.CapsuleCast.html)：扫掠查询不能代替起始重叠与地面支持检查。
- [NavMesh.SamplePosition](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/AI.NavMesh.SamplePosition.html)：最近位置投影不等于目标表面选择或可达性证明。
- [NavMesh.CalculatePath](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/AI.NavMesh.CalculatePath.html)：同步计算与完整/部分结果需要在适配层映射。
- [NavMeshSurface](https://docs.unity3d.com/Packages/com.unity.ai.navigation@2.0/manual/NavMeshSurface.html)：地面导航数据的收集与烘焙职责。

以上工程边界、后端比较和 API 是本提案的设计判断，不是 Unity 官方替项目作出的架构建议。
