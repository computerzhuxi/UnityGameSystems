# 可复用包规范

## 最小目录

    Packages/com.example.system
    ├─ Runtime/
    ├─ Tests/
    ├─ Samples~/
    ├─ Documentation~/
    ├─ README.md
    ├─ CHANGELOG.md
    └─ package.json

按需要在 Runtime 下建立 Core 和 Unity 层。每个物理源码根只归属一个 asmdef，避免程序集范围重叠。

包目录是正式功能的唯一源码归属。Lab 通过本地 UPM 引用包，不保存第二份运行时实现。Sample 与 Lab 若需要相同演示代码，应指定权威来源并通过生成或哈希检查防止漂移；更推荐让 Sample 展示最小接入、Lab 使用独立测试控制器覆盖更多场景。

## 公共接口

- 公共 API 只表达稳定能力，不暴露内部状态机或实现类型。
- 查询和命令应分离；观察者优先获得只读接口。
- 参数非法时应有明确行为，不依赖静默修正掩盖调用错误。
- 事件顺序、无变化行为、异常和重入规则必须写入 API 契约并有测试。
- 类型、字段或程序集迁移必须保护 Unity 序列化身份。
- 序列化配置必须注明仅初始化读取、运行时实时生效，或通过哪个公共命令修改。

## 测试可见性

- Runtime 不引用 Tests、Samples 或 Lab。
- 内部实现由包自己的测试程序集验证。
- 消费项目不得通过 `InternalsVisibleTo` 访问包内部实现。
- 消费项目只测试公开 API、公开组件和真实业务链路。
- 不为了测试方便扩大公共 API。

## 独立性验收

1. 运行时不引用具体游戏。
2. 在独立 Lab 中可以导入、测试和构建。
3. Sample 不依赖开发仓库之外的隐藏资产。
4. 包拥有自己的测试、说明和版本记录。
5. 消费项目只需安装或编写外部适配层，不修改包源码。
6. 从固定 Git 标签安装后的内容与发布提交一致。
7. 需要视觉或听觉判断时，存在可重复执行的人工验收清单。

## 文档要求

每个包至少提供快速入门、边界、公共 API、版本变化和一个可运行示例。复杂包应补充架构、集成、迁移和故障排查文档。版本事实来自 `package.json`，兼容变化来自 `CHANGELOG.md`，不要在多处手工维护“当前最新版本”。
