# 可复用包规范

## 最小目录与边界

    Packages/com.example.system/
    ├─ Runtime/
    ├─ Tests/
    ├─ Samples~/
    ├─ Documentation~/
    ├─ README.md
    ├─ CHANGELOG.md
    └─ package.json

包目录是正式功能的唯一源码归属；Lab 通过本地 UPM 引用包。每个物理源码根只归属一个 asmdef。仅在真实存在独立纯逻辑边界时拆 Core/Unity；依赖 Unity 物理或生命周期的程序式入口不必硬拆为纯 C#。Sample 与 Lab 若确需复制演示文件，应列出权威来源与具体镜像文件并自动检查；Lab 场景、Prefab 可以有独立职责。

## 公共接口与双入口

- 组件式入口提供通用 Inspector/序列化装配；编程式入口让调用者经公开类/接口自行组合驱动。两者共享规则、事件语义和权威状态，不维护互相同步的两份事实。
- 公共 API 只表达稳定能力；查询与命令分离，观察者优先使用只读接口；不为统一外形公开内部状态机。
- 明确非法输入、无变化、事件顺序、异常、重入及生命周期行为，并针对公共契约测试。
- 序列化配置注明初始化读取、运行时实时生效或通过哪个命令修改；迁移类型、字段或程序集时保护 Unity 序列化身份。

## 测试职责

|层次|目的|
|---|---|
|Contract|在包测试中证明规则、边界、事件与两个入口的共同语义。|
|Integration|在 Lab 与消费项目通过公开 API、真实组件、场景和 Prefab 证明装配及业务链。|
|Validation|在候选发布时验证独立导入、构建、冒烟、固定标签及需要的人工视觉/听觉结果。|

这些是验证用途，不要求建立新目录或新测试框架。内部实现只向包测试开放；消费项目不通过 `InternalsVisibleTo` 访问包内部，也不为测试方便扩大 API。

测试方式、验收证据与停止条件见 [测试规范](TestingStandard.md)。

## 文档职责

- `README.md`：安装方式和文档导航，避免复写完整契约。
- `Documentation~/GettingStarted.md`：组件式与编程式的最小可运行用例、生命周期及选择条件。
- `Documentation~/API.md` 与 `Contracts.md`（可按包合并）：公开 API、行为边界、事件与状态所有权。
- 其他架构、集成、迁移和排障专题按复杂度维护；`Samples~` 提供可运行例子。
- `package.json` 表示当前源码版本；`CHANGELOG.md` 写变化；固定发布标签及历史报告证明已发布状态。不要在多处手工维护“当前最新版本”。

独立性验收还应覆盖：无具体游戏引用、Lab 独立导入、Sample 无隐藏资产、固定 Git 标签内容一致，以及适用时可重复执行的人工验收。
