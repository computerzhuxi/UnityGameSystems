# UnityGameSystems 仓库架构

## 目标与职责

本仓库维护可被多个 Unity 项目安装的独立系统。`Packages/<package-id>` 是正式运行时、包测试、Sample 和随包文档的唯一归属；`Projects/<Lab>` 以本地 UPM 路径引用包，用于导入、序列化、场景、构建和人工观察；`Documentation` 与 `Tools` 管仓库级规范与验证。包不得反向依赖 Lab 或具体游戏。

消费项目安装固定 Git 标签或明确的候选提交；Lab 引用当前本地源码。这两种安装方式分别验证发布内容和开发中内容。已发布标签不移动。

## 双入口与状态所有权

- **组件式入口**：通过 MonoBehaviour、Inspector、序列化配置与 UnityEvent 等装配通用功能。
- **编程式入口**：通过公开类、接口和明确命令自行组合、驱动功能；可使用 Unity 类型，不强制纯 C#。
- 两种入口应遵守同一规则、事件顺序和生命周期约束。组件可以委托规则对象，调用者也可以直接组合公开对象；每份运行中事实只由一个权威对象拥有，不在适配层复制可写状态。
- 公开稳定能力及必要只读契约；内部状态机和辅助实现保持内部。是否拆 Core/Unity 程序集取决于真实纯逻辑边界，不为形式统一拆包或拆程序集。

跨模块查询优先用只读契约，写入走明确命令。序列化字段应标明是初始化配置、运行时实时配置，还是需经公开命令修改。组件的 Awake、Enable/Disable、销毁与程序式对象的创建、绑定、释放应有明确对应关系，避免多次订阅、重复初始化或隐形第二份状态。

## 依赖与验证边界

1. Runtime 不引用具体游戏、Tests、Samples 或 Lab；测试和 Sample 仅依赖运行时。
2. 包内部实现由包测试验证；消费项目只通过公开 API、真实组件和业务链路验证。
3. Sample 展示最小接入，Lab 承担开发与验证；必要镜像需指定来源并自动核对，Lab 场景可独立维护。
4. 公共 API、程序集、字段或类型变化应审查 Unity 序列化身份与消费项目迁移成本。

## 文档与版本事实

包 README 是导航；`Documentation~/GettingStarted.md` 说明两种入口；API/Contracts 文档写公开行为；其他专题按需要维护。仓库文档回答如何开发、验证和发布，历史验收归档到 `Documentation/History`，原始日志写入被忽略的 `Artifacts`。

`package.json` 是当前源码版本，`CHANGELOG.md` 记录变化；已发布版本由不可变标签及发布历史证明，消费项目的实际依赖由 manifest 与 lock 文件证明。不要把当前源码版本自动写成最新已发布版本。
