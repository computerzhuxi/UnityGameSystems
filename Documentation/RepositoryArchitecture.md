# UnityGameSystems 仓库架构

## 目标

本仓库维护能被多个 Unity 项目直接安装的独立系统。每个系统都应具备明确边界、稳定公共接口、独立测试宿主和不可变发布版本。

    游戏项目 ──安装固定版本──▶ UPM 包
                                  │
    开发工程 ──本地引用───────────┘

## 内容分类

|位置|职责|是否随包发布|
|---|---|---|
|Packages/<package-id>|正式运行时、测试、示例和随包文档|是|
|Projects/<lab>|开发、导入、序列化和构建验证宿主|否|
|Documentation、Tools|仓库级规范、发布流程和自动化|否|

正式功能必须位于包中。Lab 可以引用包，但包不得引用 Lab、ARPG 或其他具体游戏。

## 推荐分层

    具体游戏适配层 ─────────────▶ Core
    通用 Unity Component ───────▶ Core
    Core ───────────────────────▶ .NET 标准库

- Core 保存规则和唯一权威状态，不依赖 Unity。
- Unity 层负责 MonoBehaviour、Inspector、UnityEvent 和序列化接入。
- 游戏差异留在消费项目的适配层，不进入公共包。

并非所有系统都必须拆成 Core/Unity 两层；只有确实存在纯逻辑边界时才拆分。

## 依赖规则

1. 包运行时不能引用具体游戏项目。
2. Core 不能引用 Unity 程序集。
3. 测试和 Sample 可以依赖运行时，运行时不能反向依赖它们。
4. 一个事实只能有一个数据拥有者，适配层不得复制权威状态。
5. 跨模块读取优先使用只读契约，写入通过明确命令完成。
6. 已发布标签不可移动；消费项目通过标签和锁文件选择升级。

## 文档职责

包内文档随包交付，回答如何使用和集成。仓库级文档回答如何开发、验证和发布。某次发布的结论归档到 Documentation/History，原始日志保存在被忽略的 Artifacts。
